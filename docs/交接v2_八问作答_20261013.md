## Q1 查表消费端怎么最便宜（到达顺序表 / 预算表）

**结论**：表放**普通全局显存的 int32 设备缓冲**，kernel 以指针参数接收、消费点
`tl.load` 按需读——与 Syncopate 的 wave 查表完全同形态；每 forward 由宿主从 pinned
缓冲异步更新一次。不需要 constant memory（triton 未暴露）也不需要 shared memory
（表只有几十字节，L2 命中即近零成本）。第一版落在 **fused 的消费者**
（`gemm_allreduce.py:kernel_ar_consumer_reduce`）或 **AG tr 消费者**
（`gemm_ag_tr.py:kernel_gemm_ag_tr_consumer`）——mono 没有可插点（RCCL 内部决定
消费序，我们无 kernel 内消费顺序自由度），而我们自己的两个消费者 kernel 里"访问
顺序"只是一个 swizzle 计算，换成查表是局部改动。

**具体设计**：
- **表内容**：到达顺序表 `order[R]`（int8 足够，存 rank 的预期到达序）＋每 rank
  自旋预算 `budget[R]`（int32，单位=混合自旋的探测次数）＋本 forward 的 MPC/k。
  R=8 → 8+32=40 B；R=64 → 512 B。**大小完全不重要**。
- **放哪**：全局显存设备张量（普通 `torch.zeros` 即可，无需对称堆——消费者只读
  本 rank 的表）。
- **怎么传**：kernel launch 参数带表指针（Syncopate 形态：`wave_offset` /
  `cur_wave_size` / `signal_offsets` 全是设备张量参数，`template.py:82-88` 每次 wave
  边界 `tl.load`）。宿主侧每 forward 一次更新：预测器在 CPU 上算完（查迟到惯性表，
  每 forward 一次、近零开销——交接 §3）→ 写 pinned 张量 → `copy_(..., non_blocking=True)`
  异步 H2D（µs 级 engine op；同量级实测参照：引擎每-op 开销 ~30µs【S4 findings §2 表】，
  且可与当前 forward 的执行重叠，不在关键路上）。
- **消费点成本**：每个（tile/chunk）边界 1 次 `tl.load`。同型已量产：`gemm_rs_v5.py`
  的 `kernel_ack_slot` 每 ack 从全局表读 R−1 个 int64 表项，S15 全程无异常【实测】。

**与 Syncopate 先例的差异（交接 §4 指认的结构同构点）**【代码实读
`syncopate/computation/gemm/template.py:82-88`】：
1. 它的表是**静态 wave 几何**（这个 wave 算 C 的哪块、对应哪个信号槽），图构建期
   定死；我们的表是**动态到达序+预算**，每 forward 换内容。
2. 它每个 wave **无条件** `dl.wait`（纯阻塞自旋，`communication_context.py:160` 同款，
   wait 侧零作为）；我们按预算决定"等/让/跳过"——预测已到的源一次原子探测即过，
   预测迟到的源排最后等。
3. 它的查表服务"**算哪块**"；我们的查表服务"**按什么顺序等谁、等多久**"。省掉的
   是对迟到者的无效自旋：先消费早到源的数据，迟到源的等待被已排入的有用计算掩护
   （依据：短/中 prefill stayIn≈1.0——一个 forward 的前几个 AR 即锁定全 forward
   straggler【msweep §3 F4】；decode p_stay=0.98【msweep §2 主表】）。

**可行性/工作量/依赖/风险**：
- 可行性：高——全部构件（设备表参数、tl.load 消费、pinned 异步更新、混合自旋）
  单独实测过，组合无新机制。
- 工作量：消费者 kernel 内把 rank swizzle 换成 `order[]` 查表 ≈ 1-2 天（含 S8 注入
  框架复跑）；预测器输出格式对齐是推理线接口工作。
- 依赖：推理线预测器（hazard 表）的输出格式；S8 注入框架做收益验证。
- 风险：ph7 类去相关段（stayIn 0.146-0.331【msweep §2】）表过期。**关键性质**：
  预测错不损正确性——fp32 求和可交换，顺序错只是次优；预算错只是多付一次探测。
  这比"预测错退回基线"（StragglAR 兜底）还弱化的代价结构，天然带降级。
- 标注：机制构件全【实测】；"预测命中→省 X µs" 的收益数值**未测**（需
  S8 注入 × 表驱动消费者一轮实验，2 卡即可跑）。

## Q2 "有预算的自旋"在 gfx936 上的让出机制（P9 修法）

**结论**：已实测的最好让出 = **根本不占 SM**——`hipStreamWaitValue32` GTE 流等待
（S12 起三算子默认模式）：消费者 kernel 在旗标落地前不上设备，等待期设备上零自旋
wave。这是 P9（自旋消费者饿死同卡生产者【S6.4 坑 3】）的**类别级消除**而非缓解。
SM 内让出的实测形态 = CTA 预算 + 混合自旋；ISA 级 `s_sleep` 未测，是唯一还值得补的
让出原语。

**让出机制菜单**（逐条标出处）：
1. **流等待（零 SM）**【实测，S12 首试即成，`tests/test_gemm_ar_rd.py` GTE 平面探针】：
   `hipStreamWaitValue32(stream, own_ptr, val, GTE, mask=0xFFFFFFFF)` 等自己堆上的
   旗标，peer 的 4 B 引擎写可直接释放它。注意 `common_ops.wait_eq` 的 4 参绑定是错的
   （mask 落在 flags 槽，首调报错、从未被跑过），`gemm_ar_rd.py:_wait_value_gte`
   带 5 参正确绑定。
2. **宿主引擎信号唤醒**【实测】：引擎写（4 B memcpy 或 `kernel_flag_xchg`）落在本
   rank 对称堆旗标 → 流等待释放 / 自旋看到。两态都验过（S12 引擎写、S15 kernel 写）。
3. **CTA 预算**【实测，S15】：RS v5 稳态消费者预算 `clamp(tiles//4, 6, 24)`——固定 6
   在 448-tile chunk 上落后生产者 ~15 ms（39.42 ms 总时），auto 后 31.11 ms。P9 的
   原始修法 = grid 预留 2 CU + 生产者先提交【findings §P9】。
4. **混合自旋**【实测，S3 起量产】：128 次 volatile（乐观延迟）+ 1 次
   `tl.atomic_add(fp, 0)`（L2 一致性点，保证前进）。修掉 RMW 自旋挡引擎写（P8）与
   volatile 持续自旋死锁（P8.2）两类病理。
5. **`s_sleep`（inline_asm）**【未测】：gfx936 ISA 有 `s_sleep`（GCN3+ 指令，`__nanosleep`
   的 AMD 对应），triton 走 `tl.inline_asm_elementwise` 可发。预期收益有限：睡眠 wave
   仍驻留（VGPR/槽位不释放），只降 issue 与原子占用——优先级低于 1/3/4。值得一个
   半天级探针（自旋循环里插 s_sleep 对比混合自旋）。
6. **green context 按 SM 划分**（Syncopate `split_green_ctx.py:141-156` 先例）【不可用】：
   NVIDIA 专属；DCU 栈未暴露对应物。我们的对应物 = CTA 预算（机制 3）。

**StragglAR"条件执行退化到基线"可否借为降级路径**：可借，且我们的代价结构更好。
它的兜底是"前 n−1 就绪者先跑 RS，选错只退化为基线性能"（【盲区详解 §4.4】差异①，
离线选 straggler、无在线预测）；我们的表驱动消费在预测错时**退化为次优顺序而非
基线**（正确性由求和可交换性保证，延迟只差一个消费顺序）。借的是"预测必须带无损
退化路径"的设计原则——与 I1 的 ph7 自动降级（板上行）同一个约束的两处实现。

**风险**：流等待在 8 卡/多流高并发下的行为（嵌套 GTE 数量、与引擎队列交互）只做过
2 卡验证【实测范围声明】；S15 发现的 DTK26.04 运行时 wedge（微小 4 B `hipMemcpyAsync`
在深队列下宿主侧卡死，【S15，`tests/dbg_rs_big.py` 定位】）提示运行时边界尚未摸完，
8 卡首批实验应含压力探针。
**标注**：1/2/3/4【实测】；5【未测】；6【不可用】（栈不暴露）。

## Q3 单相信号落地（数据 + 尾部旗标一次写）

**结论**：三条路线，**首选宿主侧流式 put+signal**：DTK26.04 的宿主库已带 NVSHMEM 风格
整族 `dushmemx_{half,int32,...}_put_signal[_nbi]_on_stream`（数据+信号一次调用、流序、
语义=信号在 payload 之后可见）【nm 实证，符号齐全；行为未测】。内存序要求由 API
内部承担：非 nbi 阻塞版自带完成语义；nbi 版须 `dushmem_quiet`/`dushmem_fence` 收尾
（符号均在【nm 实证】）。**零新 API 的退化版**（自拼尾旗标）：发送缓冲尾预留 4 B，
一次 `putmem` 把 `[data|flag]` 连续区整体写过去——单条消息内序天然成立，接收端自旋
尾字即可；与我们现有"数据引擎 memcpy + 信号单独 RMA put"（S5.3 零悬崖模式【实测】）
相比省一次 RMA 调用、且旗标不再单独占引擎队列。

**跨机 ibgda 设备发起是否可行**：transport 插件存在
（`/opt/dtk-26.04/lib/dushmem/dushmem_transport_ibgda.so` + 构建串
`DUSHMEM_IBGDA_SUPPORT=ON`【ls/strings 实证】），且 ibgda 的设计初衷就是 GPU 显存
直发 RDMA——但**设备发起整类在机内实测有 19.5MB/s 字节率天花板**（【S4 findings §P5】
大块 putmem_signal/nbi+quiet 全部 19.1MB/s；【S6.2】微型原子可流水 1.3µs/op 但字节率
同样压线 19.5MB/s）。跨机行为**未测**（环境无跨机）；不建议作首版依赖，值得一个
vcjob 探针。
**绕 19.5MB/s 的已验路径**＝信号不设备发起：宿主引擎 memcpy（本机 110GB/s【S4】）、
宿主 RMA putmem（108GB/s【S4】）、S15 新增的 1-CTA `kernel_flag_xchg`（设备侧但走
peer VA 普通原子 `tl.atomic_xchg`，实测正确 28/28+6/6【S15】；**速率未测**）。

**与 FlashOverlap 独立计数数组 + atomicCAS 清零逐点对比**【代码实读
`src/overlap/gemm_with_signal.h:344-351`、`src/wait.cuh:5-8`】：
| 维度 | FlashOverlap | 我们（I4 形态） |
|---|---|---|
| 写侧 | epilogue 每 tile 对**独立计数数组** `atomicAdd`（:344-351）——信号内存与 payload 分离，每 tile 一次设备发起原子 | 旗标并入 payload 尾 / 同一 `put_signal` 调用——信号字节与数据同消息，零额外内存往返 |
| 读侧 | 单线程 `atomicCAS(addr, that, 0)` 自旋**兼清零**（wait.cuh:5-8，`__nanosleep(100)` 退避）——旗标复用需清零回合（一次 RMW） | 单调 ticket + GTE ≥ 比较，**永不清零**；等待可放在流上（零 SM，见 Q2） |
| 粒度 | per-tile（~128×128） | per-chunk/panel（可控，`PANEL_BYTES_CAP`=8MB【S12】） |
| 在 DCU 上 | 写侧是设备发起原子 → 落在实测 19.5MB/s 慢路径类（与 TokenWeave 每 CTA 每 rank 一次 CAS 粗粒度摊薄互证【盲区详解 §6.1】） | 信号骑宿主引擎/RMA（S5.3 实测零悬崖） |

粒度差异（tile vs chunk）是设计选择不是纯优劣；但在 19.5MB/s 栈上它的"细粒度+设备
发起"组合不可用，这正是 I4 在本栈的立足点（措辞按纪律带粒度与排除项：FlashOverlap
已核为"独立计数数组、不内嵌 payload"）。

**需要的 fence/quiet**：nbi 变体后必须 quiet/fence 才保证对远端可见序；现有引擎
memcpy + `kernel_flag_xchg` 路径靠流序（数据 op 在前、旗标 kernel 在后）——且 launch
边界顺带 retire 前驱访存（S15 ack 竞态修法，见 Q8-2）【实测】。
**首个实验**（2 卡即可）：`put_signal_on_stream` vs（引擎 memcpy + putmem 信号）的
延迟/悬崖矩阵，照 `bench/s5_signal_probe.py` 模板；顺带补 `kernel_flag_xchg` 的速率。
**标注**：符号/构建串/插件【实测】（nm/strings/ls）；put_signal 行为与速率【未测】；
19.5MB/s 与引擎/RMA 速率【实测】；FlashOverlap 对比【代码实读】。

## Q4 无源 wheel 的能力边界（哪些设备 API 已验证可从 triton kernel 调）

**结论**：两条已验证通道（extern 位码链 DUSHMEM 设备 API；裸 triton 原子写 peer VA）、
一条指令级通道（inline_asm，未测）、一张负面清单。上游 `async_task`（`dl.wait`/
`st(semantic="release")`，编译器后端扩展）在闭源 wheel 上不存在【S6.1 结论】——它的
**运行期**等价物已全部落地（见替代路线清单）。

**已验证可从 @triton.jit 内调用的 DUSHMEM 设备 API**（经 `extern_libs` 位码链接配方，
findings §P1 全套坑位）：
| API | 状态 | 出处 |
|---|---|---|
| `dushmem_putmem_nbi` + `dushmem_quiet`（kernel 内） | 可调、正确 | 【S3】scatter kernel 量产（`gemm_reduce_scatter.py`） |
| `dushmem_*_atomic_set` 家族（8B uint64 等） | 可调、可流水 | 【S6.2】探针：512 CTA×2 时 1.32µs/op |
| `putmem_signal` / `putmem_nbi+quiet` / +atomic_set（大块） | 可调、**全部 19.1MB/s** | 【S4】`s4_transport_probe.py` |
| `getmem_nbi`（设备拉取） | **VMFault，不可用** | 【S4】 |
| 全部设备发起传输 | **19.5MB/s 字节率天花板**（与 op 无关） | 【S4/S6.2】 |
| 裸 `tl.atomic_xchg` 写 **peer 对称堆 VA**（非 dushmem API，走 peer 映射普通原子） | **可调、正确**（AG 28/28、RS 6/6）；速率未测 | 【S15】`kernel_flag_xchg` |
| `tl.inline_asm_elementwise` 发 `s_sleep` 等 ISA 指令 | 未测（通道本身是 triton 标准能力） | — |

注意最后第二行是 S15 新发现的**第三通道**：它不走 dushmem proxy（避开 19.5MB/s
管道），是"设备发起写 peer"唯一已知不踩天花板的形态——但只验过正确性，速率与
扩展性（多 CTA 并发写）待探针。

**async_task 替代路线清单**（上游"编译期把通信融进 kernel"→ 我们的运行期对应物）：
1. extern 位码调 DUSHMEM 设备 API（上表；数据面受天花板限，只适合微信号）；
2. 流等待 `hipStreamWaitValue32`（零 SM 等待，【S12 实测】）；
3. 混合自旋 kernel（【S3-S15 量产】）；
4. 1-CTA 旗标 kernel `kernel_flag_xchg`（【S15】）;
5. 宿主编排引擎 memcpy（主数据面，110GB/s【S4】）；
6. `dushmemx_*_put_signal_on_stream` 宿主侧单相（【nm 实证，未测】，见 Q3）。

**边界一句话**：无源 wheel 剥夺的是**编译期融合**这一层；**运行期融合**（多流编排 +
旗标/ticket）全部可用且已实证——这正是 paper#1 的宿主编排架构在此栈上反而顺手的
根本原因（S12-S15 三个算子全程零全局 barrier、零宿主阻塞同步）。
**标注**：除注明外全【实测】。

## Q5 fused 合并 kernel 砍 CPU 发起开销的量化（decode 其余段 22% / prefill 34%）

**结论**：可量化的锚都在，外推部分明确标注。本栈三个实测锚：
(a) **4-op torch 链纯宿主启动 0.13ms ≈ 32µs/op**（`reshape→.long()→bincount→.to`，
【S7】`s7_meta_decompose.py`）；(b) **torch `wait_stream` 10-40µs/次**，裸
`hipEventRecord/Wait`（DISABLE_TIMING）1-4µs（【S11】evtax 探针）；(c) 多 fork/join
一组**不用的**流 ~0.1ms 宿主提交（【S13】教训 d）。

**forward 的 kernel 数结构**【推断，锚在实测结构】：每 forward 161 次 AR = 80 层×2+1
【msweep §1 实测计数】；每层 4 个 TP 线性 GEMM（qkv/o_proj/gate-up/down）+ attention
+ norm/act ≈ 10-15 kernel/层 → 全 forward ≈ **800-1500 次 kernel launch**（结构数出，
未逐 kernel profile）。其余段 decode 24.4ms【交接 §1 实测】÷ ~1000 ≈ **24µs/launch
槽位**——与锚 (a) 的 32µs/torch-op 同量级，自洽【推断】。

**fused 能砍多少（按 kernel/派发数）**：
- 每对 (GEMM+AR)：mono = 2 次 python 派发（`torch.matmul` + `dist.all_reduce`，各带
  c10d/RCCL 入队层）；S6 fused = 1 次 python 入口、内部 ~15 次宿主 API 调用，**且含
  一次宿主阻塞 `evs_data[-1].synchronize()`**（`gemm_allreduce.py:411`）——这是 fused
  当前形态的宿主税。S12+ 形态（AR rd/RS v5/AG tr）已消灭：**全程入队即返、零宿主
  同步**【实测，S12-S15 代码】。
- 消费者 **epilogue 折叠**：RMSNorm/residual 可折进 `kernel_ar_consumer_reduce` 的
  写回段（改一个 kernel 尾部，无新机制）→ 每层再省 2-4 个 launch。
- 上界（整层 megakernel，FlashMoE 形态）：~15 kernel/层 → 1-2，launch 数 ~8×↓；但
  通信面进 kernel 受 P9 预算 + 设备发起 19.5MB/s（Q4）约束，DCU 版只能走 peer-VA
  原子/引擎信号混合——这是 I6 的研究问题，不是现成红利。
- **诚实估算**【推断】：每 AR 对省 1 次派发（~32µs）+ 可折叠 norm launch（~24µs）
  ≈ 40-70µs/对 × 161 对 ≈ **6-11ms = decode 其余段 24.4ms 的 25-45%**；prefill 同
  计数（161 对），其余段 48.1ms 中 launch 占比更高（GEMM 段 launch 密集），绝对
  节省同量级、相对占比略低。
- **前提**：fused 必须以 S12+ 无宿主同步形态为基线——否则砍掉 python 派发层的同时
  把宿主阻塞同步加回来了（S6 形态的教训就在代码里）。
- **零卡可做**：用 ph1 的 189MB trace 数 kernel 数、对 CPU 栈做 launch 成直方图，
  把上面的推断换成实测（推理线 trace 在手）。
**标注**：(a)(b)(c)【实测】；forward kernel 计数与收益外推【推断】；逐 kernel
profile【未测，零卡任务可闭合】。

## Q6 I6（MoE all2all 解耦面）vs FlashMoE 差异化

**结论**：四条差异化全占（域/测量预测/调度/栈）；DCU 上值得以 Triton 重做的三件、
明确放弃的一件。

FlashMoE 形态【盲区详解 §8 全文核查，推理线】：单 megakernel 融合
gate→A2A→专家FFN→A2A，NVSHMEM+CUTLASS，8×H100，T=4K-16K，straggler ECDF 仅作动机
（无预测、无等待期回收）。

**差异化清单**：
1. **域**：decode/小 T（T=4-2048；`bench/s7_bench_moe_a2a.py` 已有 T128-T2048 全套
   【S7 实测】）vs 它 T≥4K。
2. **kernel 内偏斜测量+预测**：它零作为。MoE 的"δ"=专家负载不均，观测面就在
   dispatch 直方图里——我们的 `kernel_pack_meta`（单 CTA 融合清零+直方图+打包+旗标，
   meta 0.46→0.29ms【S7 实测】）**顺手就能产出热度表** = I6 预测器的免费数据源。
   热度 Zipf 且粘【猜测，板上已标"待验证"】→ 预测故事比 decode straggler 更强。
3. **偏斜感知调度**：段序/推送序按热度排（元数据面已算出段表，排序是宿主侧改动）。
   它无对应物。
4. **DCU 栈**：它 H100+NVSHMEM 设备直发全速；我们 19.5MB/s 约束下的宿主引擎面。

**值得以 Triton 重做的三件**：(a) dispatch 段压拢 + per-dest 单 engine memcpy
（【S7 实测】2 卡 2.34×/2.9× vs RCCL；8 卡反转 2.9× 慢——扇出墙 17-25GB/s/rank
【S9】，对症药在 Q7 环形/分层）；(b) combine PULL（peer VA 直读 warm 74-83GB/s、
首触 160-335ms 由 `k_touch` 预付【S7 实测 `s7_peer_load_probe.py`】）；(c) 元数据面
单 CTA 直方图（上表，含热度表副产物）。
**放弃**：把专家 FFN 计算也塞进通信 kernel 的 megakernel 化——它的融合通信靠
NVSHMEM 设备 put 全速，我们设备发起数据面 19.5MB/s 判死【S4/S6.2 实测】。DCU 正确
形态 = 解耦面（宿主引擎推送 + pull 消费）+ 专家计算独立 GEMM，即 S7 现架构。它的
"融合"卖点在本栈不可移植——这是差异论文素材，不是劣势。
**节奏**：MoE 是第二幕（板上已定）；8 卡扇出墙（环形路线）落地前端到端倍数难看
（2 卡赢/8 卡输的现状态），I6 收尾应排在 Q7 之后。
**标注**：S7 全部【实测】；FlashMoE 对比【推理线全文核查】；热度粘性【猜测】。

## Q7 多机解耦面的拓扑分层（机内 xGMI 单侧 + 机间 ibgda 双平面）

**结论**：**API 面已实证存在**；分层方案 = **单次 DUSHMEM 初始化 + 双 team**
（机内自动成团的 `DUSHMEM_TEAM_SHARED` + `dushmem_team_split_2d(机内数, 机间数)`），
不开双实例。数据面：机内 = 引擎 memcpy peer VA（110GB/s【S4 实测】）；机间 =
on-stream RMA（`putmem`/`put_signal_on_stream`；**跨机速率未测**，环境无跨机）。

**API 实证**【nm/strings/ls 于 `/opt/dtk-26.04/lib/dushmem`，2026-10-13】：
- 符号全在：`dushmem_team_split_2d` / `team_split_strided` / `team_translate_pe` /
  `team_sync` / `dushmemx_team_sync_on_stream`；`dushmem_fence`/`quiet`；
  `dushmemx_{dtype}_put_signal[_nbi]_on_stream` 全族；`dushmemx_int32_wait_until[_all]_on_stream`。
- `DUSHMEM_TEAM_SHARED` 自动从 P2P 表成团（字符串证据 "DUSHMEM_TEAM_SHARED:
  start/stride/size"；不成团时回退 self）；`DUSHMEM_MAX_TEAMS` 可调。
- transport 双插件都在：`dushmem_transport_ibgda.so` + `dushmem_transport_ibrc.so`，
  构建串 `DUSHMEM_IBGDA_SUPPORT=ON / DUSHMEM_IBRC_SUPPORT=ON`。
- 行为/性能**全部未测**（符号在 ≠ 驱动配好 ≠ 快）。

**anchor 跨节点最长杆先走**：S12 RD 相位序是 XOR 固定；分层版 = 同 rank 的任务序里
**跨节点 partner 的 panel 推送排在机内 partner 之前**（跨机 wire 92µs vs 机内
13-50µs【msweep §2 + ③ 实测】），让最慢链路最早出发。实现 = 任务排序变化 +
`team_translate_pe` 做 pe 映射，无新机制。
**双 comm vs 双实例**：推荐单实例双 team。双实例 = 双 proxy 线程 + 双对称堆（单堆
上限实测 ~1.8GB/rank【S9.1】，翻倍即爆）+ bootstrap 复杂化；team 路线堆共享、槽池
一次管理。

**对称槽池三路并发的 k 预算**（按实测 δ/wire 组合【推断】）：
| 路 | 消息/槽字节（实测依据） | k 预算 | 依据 |
|---|---|---|---|
| decode AR | M=4-16 tok × N=8192 × 2B ≈ 64-256KB/槽 | **k=2**（跨机可 k=4） | 吸收窗 w(k)=270/468/827µs【S8 实测】；δ p50 360-510µs 单机【msweep】/534µs 跨机【③】→ k=2 的 w=468 略欠、k=4 富余 |
| logits allgather | [B, V/R] ≈ 128-512KB | **k=1** | 每步一次、单 chunk 即可 |
| prefill chunk AR | 33.6MB/chunk（M=2048 chunk【msweep §1】） | **k=4，panel 化 8MB/panel**（`PANEL_BYTES_CAP`【S12】） | w(k=4)=827µs ≥ δ；panel 化后槽 ~4×8MB=32MB/方向 |

峰值 ≈ decode 数 MB + logits 数 MB + prefill ~32-140MB ≪ 1.8GB 堆上限【S9.1 实测】，
给 MoE a2a（T1024/H4096 时 recv+out ~1GB【S9.1 实测最大分配】）留路；三路并发峰值
（prefill 与 decode 交错）按 worst-case 同时持有核算，k 预算做成运行时配置表
（每路 [k, slot_bytes]，create 时从池划）——对应创新板"分配层落点 1"。
**工作量**：team API 的 ctypes 绑定 1-2 天（照 `pydushmem/host.py` 现有模式）+ 一批
双机 vcjob（DUSHMEM MPI bootstrap 跨机冒烟 → 跨机 putmem 速率探针照
`s4_transport_probe.py` 模板 → team 冒烟）。
**依赖**：双机 vcjob 卡时（板上节奏第二批）。
**风险**：(a) ibgda 在 BW1000+实际 NIC 组合的可用性；(b) TEAM_SHARED 成团依赖跨机
拓扑暴露后的 P2P 表正确性；(c) **跨机没有引擎 memcpy**（peer VA 不可 hip 直达）——
机间必须换 RMA 面，混合编排复杂度上升，`put_signal_on_stream` 若可用则一步到位
（Q3）；(d) 1.8GB 堆跨机是否同限未测。
**标注**：符号/插件/构建串【实测】；一切跨机行为【未测】；k 预算=实测参数的推断组合。

## Q8 迁移中看到的内核级创新机会

按"机制级（论文可写）→ 工程级（载体稳定性）"排六条，每条带实测依据与对接的 I 点：

1. **等待卸载到流（零 SM 等待平面）**【实测，S12 首试即成，S12-S15 默认模式】：
   `hipStreamWaitValue32` GTE 在自己内存上观察 peer 引擎写的 4B 旗标——等待不再占用
   任何 SM/wave。这是 P9 的类别级消除（不是缓解），且是 **I2（等待窗算力回收）的
   使能器**：等待零占用 → 窗口天然可填。与 Syncopate 阻塞自旋（`dl.wait`）、
   FlashOverlap CAS 自旋（wait.cuh:5-8）形成三层对照——"等待本身的资源成本"作为
   可显式设计的维度（措辞按纪律带粒度与排除项，勿写裸"没人做过"）。
2. **launch 边界即 fence（1-CTA 旗标 kernel 的双重身份）**【实测，S15】：`kernel_flag_xchg`
   既是 DTK26.04 微小 memcpy wedge 的规避，又顺带 retire 前驱流的访存——修掉了
   kernel 内计数 ack 与在途弱读的竞态（rank1-chunk6 单 chunk 0.2 md 损坏 → follow-up
   ack kernel 后 6/6 干净）。上游 `dl.st(semantic="release")` 的运行期替身："用 launch
   边界做内存序"在本栈是一个可教的模式。
3. **旗标运输选择器（一致性感知传输面）**【实测矩阵，findings §4.1 立项 + S12/S15
   两个新实例】：同一逻辑旗标有 4 条物理运输——引擎 memcpy（S5.3 悬崖源）、宿主 RMA
   put（S5.3 根治）、设备 dushmem 原子（19.5MB/s 类）、kernel peer-VA 原子（S15）——
   按队列行为/一致性/速率选。8 卡下旗标面聚合行为（7 入向流）未测 = 现成下一步
   （S9 已见 AG mean≫p50 尾部复发【S9.3-4】）。对接 I4（单相信号的运输决策）。
4. **ack 方向反转（全本地等待面）**【实测，S12-S15 三算子统一形态】：free/ack 全写
   对方、等待全在自己堆、远端触碰全是引擎 memcpy——在"DCU 远端读贵"（设备 get
   VMFault【S4】、peer load 首触 160-335ms【S7】）前提下的架构适配，零远端读/零
   远端原子/零设备发起 dushmem。
5. **消费者 CTA 预算的稳态/尾态切分**【实测，S15：39.42→31.11ms】：稳态预算
   `clamp(tiles//4, 6, 24)`、尾态放开全 grid。一般化 = "消费类 kernel 的 CTA 预算按
   生产者进度分相"——与 I1 预算表天然接口（表喂 budget，Q1）。
6. **panel 字节封顶窗口**【实测，S12/S15】：`PANEL_BYTES_CAP`=8MB（256 行对齐下限）
   把"窗口工程"（w 随 k，S8）与引擎每-op 开销（单 op 带宽台阶 22→107GB/s【S11.1】）
   耦合起来 的设计参数，跨形状稳定（LLaMA 级 N 下 panel 25-29MB，cap 被地板约束，
   已评估可接受）。

对接汇总：1→I2 使能；5→I1 落点；3→I4 运输面；2/4/6→载体稳定性与工程章节。
