## 结论

1. **两卡上 RCCL+vendor 全线领先**（AG 3.2×、RS 2.3×、AR 2.6× 于我们最好算子）——
   与 S15/S17 一致：2 卡 p2p 无 fabric 墙时串行 RCCL 基线极强；我们的战场在 8 卡
   （a2a 在 2 卡已反超 3.2×，8 卡 fabric 墙时 GEMM 系同样有翻盘窗口，见 S9-S11）。
2. **差距 100% 在 GEMM 计算**：gemm_triton(consumer 形态) 39.60 vs vendor 11.00 =
   3.6×（≈106 vs ≈361 TFLOPS @29568）。通信部分 AG 0.80ms@84GB/s 是有竞争力的。
   DUMMA P0b 实测（见下）naive 60.6 TF / 去 load 结构上限 139.8 TF —— 不敌 triton
   172，tile 替换路线搁置；下一步真杠杆仍是 consumer 形态 1.8× 开销本身。
3. **预测器在稳态=纯开销**（无 straggler 可预测）：AG i1 = s14 +3.4ms（表写+观察器），
   verify 再 +2.9ms（repairs=0，与 S17 的 +4-6% 一致）；AR 载体 = rd +0.5ms。
   收益在偏斜场景（S15 rig：full7 tnv −35.3% = 98.5% oracle；强偏斜 δ=1600µs
   5.19→3.73ms）。表中数值即"预测器加持算子在无偏稳态的时延"。
4. **兼容性**：除 base RS（硬编码 256 对齐断言，gemm_reduce_scatter.py:152）外，
   全部算子 128 对齐即可跑 29568。base RS 的 28672 参考值：23.43ms（S15）。
5. AR rd 39.89 @29568 vs 33.48 @28672（+19%，N 仅 +3%）——超出 N 比例，疑似 231 tile
   的 band 几何碎片化，待查；v5 同形状只 +4%（31.11→32.31，与 N 同步）。

## DUMMA P0a/P0b（S18 前半，bench/dumma/）

- P0a（手册 fp32 m16n16k8 例程）：PASS max_abs 2.4e-7。wave64-only（du_mma.hpp 全部
  按 `__lane_id()` 0..63 编址；8×wave32 映射会得到错果+18.7TF）。
- P0b（BM128/BN128/BK32, smem 双缓冲, 4×wave64 warp×64×64, 16B 向量 load，正确
  max_abs 1.5e-5）@M8192 N29568 K8192 单卡：**60.6 TF**（load 延迟受限，仅 1 级预取）；
  NOLOAD 探针（纯 MFMA+LDS）**139.8 TF** = 该结构上限。vs triton 172 / hipBLASLt 367。
- 判定：naive DUMMA tile 不敌 triton codegen；要翻盘需 3 级环形缓冲(≥60KB smem)+
  LDS swizzle(SLD=36 消 2-way 冲突)+load/compute warp 专门化——多日工程。API 只暴露
  16×16×16 一种 half 形态（无 32×32×16）。路线带数据搁置。

## 复现

```bash
bash bench/s18_run_full.sh          # ar/rs/ag/a2a 四家族 + merge
# 单家族: S18_FAM=ag ... mpirun -np 2 ... python3 bench/s18_bench_unified.py
# a2a 变体: S18_A2A_TOPK=2 (默认; 8 装不下 1.8GB 堆)
cd bench/dumma && /opt/dtk-26.04/bin/hipcc p0b_tiled_gemm.cpp -o p0b \
  --offload-arch=gfx936 && ./p0b 8192 29568 8192   # NOLOAD=1 探针
```

已知噪音：每家族退出时 prterun 报 rank 段错误（dushmem teardown，JSON 已写完，无害）；
ag 家族若连续创建多个 i1 context 会复现 S17 级楔死（现单 ctx 复用，s18 脚本已固化）。
