## 1. 预测器原理（I1，宿主粘性到达序预测）

**观察对象**：每轮各"面板"（panel）到达本端的时间线（设备端计时事件，
非宿主轮询）。

**预测器**（`triton_dist/kernels/dcu/i1_predictor.py`，本实验用同设计的
`PanelVictimPredictor`）：
- 单元 = 本轮最晚到达的面板（victim），由到达时间线推断（首个位置散布
  或流内最大完成间隔，阈值随轮自身节拍自适应）；
- **last-vote**：预测下一轮 victim = 上一轮观察到的 victim；
- **粘性门控**：窗口 W=8 内相邻一致率 < 0.6 时降级（degrade）→ 回退自然
  序并计数（防止在去相关流上乱猜）；
- 宿主开销 <10µs/轮（last-vote 本身是 O(1) 查表）。

**消费动作（AR 传输上的等价物）**：AR 的 slot 流是串行队列
[GEMM→推快照→等到达→累加]×k。预测的慢面板**排到本流队尾**，让它前面的
就绪工作先走——这是论文 I1 表 order[] 字段的宿主侧等价实现
（`triton_dist/kernels/dcu/gemm_ar_pred.py`）。

**机制的实测形态（重要修正，tt5 双秩时间线）**：原推断"排序不可能降低整轮
墙钟（δ 总会加到某条流尾部）"只在**设备受限**下成立。实测本装置的轮子是
**宿主入队受限**：victim 早位时，其未决 wait-value **反压宿主入队线程本身**
（rank0 的到达等待入队停 ~δ、rank1 同样；t[2:] 全部拖后、以 ~90µs 入队节奏
打包）——早位 victim 把**整轮串行化**在自己的 δ 之后。预测 victim 排队尾
→ 其余 15 个面板的入队/执行完全解耦，δ 在尾部被并行吸收。因此排序**在整轮
墙钟上也赢**（§4.1 收复 93%），就绪工作指标更甚（tnv 收复 98.5%）。这比原
"边界论"更强，且给 L1 防套壳提供了时间线级的直接机制证据。

## 2. 实验装置（bench/l1_pred_ar_bench.py）

双卡 BW1000，M=16384/卡, N=2048, K=4096, CR=1024 → 16 面板, S=4 slot 流。
三臂配对设计（同 tick 同注入计划）：
- **nopred**：自然序（基线）；
- **pred**：预测器给序（冷启动/降级=自然序）；
- **oracle**：真实 victim 排尾（上界）。

注入（S8 单victim形状）：rank1 用 GTE 门压住 victim 面板的推送，δ =
tier×U(0.75,1.25)；粘性 tier ∈ {800, 3200}µs（p_stay=0.98）+ 去相关
tier 3200µs（每 tick 均匀重抽，验"降级不劣于不预测"）。
观测：rank0 对每面板记录**计时事件**（op 内每面板一次 hipEventRecord，
轮后一次批量读时间线，无在途 D2H 轮询——实测在途 4B D2H+同步在引擎负载
下 ~2s/次，不可用）。
计时：臂内设备事件对（ev_t0→ev_t1），不用宿主墙钟（入队节奏 ~90µs/面板
会污染窗口）。臂位按 3 轮换旋转对消臂位税（§5.2）。

## 3. 本轮定位并修复的两个协议级问题（均实测复现→修复→复验 0/8）

1. **重排下 ticket 必须按"执行序位"编号，不能按任务 id。**
   GTE 到达/ack 协议靠每槽标志值单调递增。任务 id 编号在 victim 排尾时使
   槽 3 的值序列变为 8,12,16,**4**（下降），victim 的等待被旧的 16 提前
   满足 → 对面累加到旧/撕裂快照。特征（实测，与预测完全吻合）：损坏恰为
   1 个面板、整面板稠密、e_std = √2×单面板贡献 std（=错内容−对内容）、
   md≈0.18；后续轮还会挂死。修复：`ticket = round_base + p + 1`（p 为执
   行序位）。**这是论文 order[] 字段的硬约束。**
2. **对端内存槽也必须按序位重键（s_nat = p % S），保持流↔槽 1:1。**
   保持自然键时，重排把一条执行流的任务摊到多个槽上，跨流 ack 耦合实测
   每轮多付 ~2-3ms。修复后仍余 ~1.3-2.5ms 臂位税（§5.2）。

修复验证：tests/dbg_rsar_soak.py `DBG_SEQ=1`（完整复刻 bench 臂序列：
自然+观测 → 自然 → victim 排尾 ×2，每轮带门、共享输出）：
**fails 0/8, worst md 0.00013**（修复前同配置 md 0.18 并挂死）。
对照实验（此前已完成）：RS v5 0/600、AR rd 0/600 全干净 → AG 撕裂是
AG 路径特有（跨卡拉取/对称堆 A 操作数/GEMM 内对端标志门），与本次
L1-AR 装置无关。

### 4.4 victim 推断（已修好，三步定位全程实测）

- 症状：vhat_ok=0/24，v_inf 稳定返回错误 id（3 或 4），v_true=1。
- 第一步（tt2）：victim=8 时时间线在 task 8 有干净 1.7ms 停顿 → 推断
  逻辑本身能命中，问题在判别序。
- 第二步（tt5 双秩时间线，v_true=1）：victim 的 δ **确实落在 t[1]**
  （4077 vs 正常 ~880），但 wait-value 反压同时把 t[2:] 全部拖后 →
  t[4]−t[0] 的"流内间隔"也被抬高（3918µs），间隔分支抢先触发返回 4。
- 修复：**首批检验优先**（victim 在首批时其 t[s] 自身膨胀），对照值取
  其余首批的 **min**（被反压拖累的同批会一起变晚，未被堵的保持早）；
  流内间隔作第二判据（中/后位 victim，首批干净、单流间隔膨胀）。
  阈值均为 `max(150µs, 2×pace)`。
- 复验：full7 vhat_ok 16/24（未命中轮 = victim 恰在轮换位 1 的平滑轮，
  δ 被吸收不可见——last-vote 窗口内由上一观测补位），tnv 收复从 4.7%
  升到 **98.5%**。

## 5. 遇到过的问题（前两个已解决）

1. **~~确定性 enqueue 卡死~~（已解决）**：第 8 个 op rank1 阻塞在
   `gemm_ar_pred_op` 入队内部。根因：victim 的 GTE 门若由 **align barrier
   之后的宿主点**释放（内联、或等待 barrier 信号的线程），而入队调用本身
   被该未决等待反压（设备队列回压→宿主 launch 阻塞）→ 自死锁（两次在
   同一 op 复现，确定性 100%）。修复：**释放线程在入队之前启动**、从入队
   起点睡 δ 后用独立引擎流写标志，完全不依赖 barrier。修复后 18-54 tick
   连跑干净，完整矩阵 ~25s 跑完。**装置级法则：任何"稍后的宿主点"释放
   方案都会自锁。**
2. **~~victim 推断稳定错~~（已解决，§4.4）**：判别序两度错排（首批散布
   → 间隔优先 → 首批-min 优先），最终判别在全部已捕获时间线上回放命中。
3. **臂位税**：第 2/3 臂比第 1 臂慢 ~1.3/2.5ms，与序无关；已用 3 轮换旋转
   对消。tt5 顺带把根因看清了一半：victim 不可见的平滑轮全部出现在轮换
   位 1（设备排空、wait-value 入队走快路径），阻塞只发生在前臂未排空时
   ——与 §1 的反压机制同源。
4. **AG-GEMM 残余撕裂未修**（任务 2）：v11 隐含 ΔA 取证代码已就绪
   （tests/dbg_i1_bisect.py），本轮无 GPU 时间跑 300 轮大形状浸泡。
